============================================================
六、Main.gd 的职责与运行结构
============================================================

文件：
res://Scene/Main/Main.gd

Main 是整个游戏的总流程控制器。

主要职责：
1. 开始菜单
2. 新游戏
3. 多槽位读档
4. 退出
5. Clinic / Night 切换
6. Story 覆盖播放
7. Story 中诊疗后端
8. 白天 / 夜晚阶段结束自动存档
9. 场景生命周期管理

重要架构：
Clinic 与 Night 是“常驻实例”。

也就是说：
- 第一次进入时 instantiate
- 后续切换时不 queue_free
- 通过 visible / process_mode 启停
- 每种场景整局通常只实例化一次

Main 中缓存：
clinic_scene_instance
night_scene_instance

这样做减少频繁实例化大场景。


============================================================
七、游戏主循环
============================================================

新游戏：

开始菜单
→ 选择槽位
→ 如有旧档则确认覆盖
→ GameTime.start_new_game()
→ Unlock.reset_progress()
→ StoryManager.load_save_data({})
→ 进入 Clinic

注意：
新游戏开始时不会立即写盘。
目前等待第一次阶段结束后生成正式存档。


正常白天流程：

Clinic
→ 接诊 NPC
→ 把脉
→ 选择疾病
→ 开方
→ 提交
→ FormulaJudge 判定
→ 诊疗奖励 / 财务记录
→ 时辰推进
→ 白天结束

正常白天结束：

Main._on_clinic_finished()
→ 当天银钱结算
→ GameTime.finish_day()
→ 自动存档
→ Night


夜晚：

Night
→ 显示当日日结
→ 检查夜晚剧情
→ 读书
→ 玩家点击“休息，进入明天”

夜晚结束：

GameTime.finish_night()
→ current_day + 1
→ 自动存档
→ 下一天 Clinic

十、GameTimeManager
============================================================

文件：
res://System/Time/GameTimeManager.gd

核心状态：

current_day
    当前日期序号

current_phase
    "day" / "night"

current_shichen_index
    当前十二时辰索引

clinic_clock_running
    Clinic 是否正在计时

clinic_clock_paused_by_story
    是否因为剧情暂停 Clinic 时钟

clinic_time_accumulator
    当前时辰累计现实秒数


Clinic 时间规则：

CLINIC_START_SHICHEN_INDEX = 4
= 辰时

CLINIC_END_SHICHEN_INDEX = 8
= 申时

CLINIC_SECONDS_PER_SHICHEN = 30.0

即：
现实 30 秒推进一个游戏时辰。


剧情进入时：

GameTime.pause_clinic_clock_for_story()

只暂停：
- 不清空时辰
- 不清空 accumulator

剧情返回 Clinic：

start_clinic_time() 检测 clinic_clock_paused_by_story
→ 恢复原时辰和累计秒数


正常重新进入 Clinic：

start_clinic_time()
→ current_phase = day
→ 时辰重置为辰
→ accumulator = 0
→ 开始计时


============================================================
十一、当前存档架构
============================================================

文件：
System/Save/SaveManager.gd
System/Save/SaveWorker.gd

当前是多槽位存档：
SAVE_SLOT_COUNT = 3

SaveManager 的设计方向是可靠的：

主线程：
- 读取 Autoload 状态
- 创建纯 Dictionary 快照
- duplicate(true)

后台线程：
- JSON.stringify
- FileAccess
- flush
- 临时文件写入
- 正式文件替换

事务文件：
.tmp
.bak

基本策略：
1. 写 temp
2. 验证
3. 旧 save 变 backup
4. temp 替换 save
5. 替换失败时尝试恢复 backup

SaveManager 还提供：
flush_async_saves()

用于这些需要“函数返回时磁盘必须已经是最新状态”的情况：
- 读档
- 删除存档
- 查询槽位
- 同步 save_game()
- 游戏退出


============================================================
十二、非常重要：当前存档只保存“阶段状态”
============================================================

当前 SaveManager 的 time 数据只有：

current_day
current_phase

目前没有保存：

current_shichen_index
clinic_time_accumulator
clinic_clock_running
clinic_clock_paused_by_story


为什么现在可以不改：

当前正式自动存档点都在阶段边界：

白天完成
→ finish_day()
→ 保存

夜晚完成
→ finish_night()
→ 保存

因此当前正式存档语义是：

“记录玩家已经到达哪个昼夜阶段”

而不是：

“完整恢复游戏运行现场”


以后什么时候必须改：

如果增加任何以下功能：

- 手动保存
- 快速保存
- Clinic 中途保存
- 暂停菜单保存
- 退出时随时保存
- 剧情中保存
- 断点续玩
- 精确恢复某个时辰

就必须扩展 GameTime 存档。

至少需要考虑保存：

current_shichen_index
clinic_time_accumulator
clinic_clock_running
clinic_clock_paused_by_story

更推荐未来改成：

GameTime.get_save_data()
GameTime.load_save_data(data)

由 GameTimeManager 自己负责序列化和校验，
不要长期让 SaveManager 一项项直接写 GameTime 字段。


如果以后支持“剧情进行中保存”，还不止是 GameTime：
还需要保存剧情当前段落、返回目标、治疗阶段等 Story 运行现场。

当前规则：
在 GameTime 存档升级以前，只在昼夜阶段边界正式存档。

十四、当前解锁规则
============================================================

UnlockManager 当前设计明确区分：

1. 医书 Entry 状态
2. 实体状态（Herb / Formula / Disease）
3. 已读状态


方剂：

unlocked_formula_ids
是“方剂实体是否已经解锁”的事实来源。

接口：

Unlock.is_formula_unlocked(formula_id)


方剂解锁后：
- unlocked_formula_ids[id] = true
- clinical_log 对应状态同步
- 匹配的 FormulaBookEntry 同步解锁


疾病：

unlocked_disease_ids
是疾病实体的事实来源。

疾病通常由推荐方剂解锁状态驱动。


医书条目：

unlocked_entry_ids
代表条目可见/已解锁

read_entry_ids
代表是否已经阅读


不要把：
formula_id
和
entry_id

在逻辑上当成同一种 ID。

十五、Prescription / 预制方剂

PrescriptionWindow：

- 方剂按钮缓存

预制方剂有“两层解锁”：

第一层：功能开关

FORMULA_FILL_FEATURE_ENTRY_ID = "yu_zhi_fang_ji"

判断：
Unlock.is_entry_unlocked(FORMULA_FILL_FEATURE_ENTRY_ID)

含义：
“玩家有没有获得使用预制方剂功能的资格”


第二层：具体方剂

判断：
Unlock.is_formula_unlocked(formula_id)

含义：
“这个具体方剂实体是否已解锁”


正确关系：

御制方剂功能条目已解锁
AND
具体 Formula 已解锁
AND
搜索词命中

→ 才显示【方剂】按钮


点击方剂后：
先完整验证所有组成药材：
- herb_id
- Herb 是否存在
- amount > 0
- unit 是否有效

只有全部通过后才：
current_prescription.clear()

然后按：
君 → 臣 → 佐 → 使

统一填入。

这是一个比较好的“先验证、后修改”结构，
避免中途发现坏数据时破坏玩家原处方。

二十二、非常重要：一个修复目前没有进入 GitHub main
============================================================

【未进入当前 main】
UnlockManager._load_bool_dictionary()

我们之前给用户制作过一个本地覆盖版，
建议逻辑是：

只有 bool(source[key]) == true
才加入 result：

if bool(source[key]):
    result[clean_key] = true


但重新检查当前 GitHub main 后，
仓库现在仍是：

result[clean_key] = bool(source[key])


因此 GitHub 当前版本仍存在这个兼容性隐患：

如果旧档 / 编辑档 / 异常档中出现：

{
    "some_id": false
}

读取后：
some_id 这个 key 仍然存在。

而很多解锁判断使用：

dictionary.has("some_id")

于是 false 也可能被当作“已解锁 / 已读”。


结论：
这项修复目前应该仍视为待提交。

未来处理优先级：高于一般代码清理，但不是正常新存档的立即崩溃问题。


推荐最终实现：

func _load_bool_dictionary(source) -> Dictionary:
    var result := {}

    if typeof(source) != TYPE_DICTIONARY:
        return result

    for key in source.keys():
        var clean_key := String(key).strip_edges()
        if clean_key == "":
            continue

        if bool(source[key]):
            result[clean_key] = true

    return result

二十九、给未来 ChatGPT 的最短摘要
============================================================

这是一个 Godot 4.6 中医行医游戏。
